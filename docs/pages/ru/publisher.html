Как опубликовать аддин Fusion для Community Store

English · Community Store

Руководство для авторов и поставщиков, которые уже умеют собирать аддины Autodesk Fusion. Оно поможет подготовить GitHub-репозиторий, чтобы пользователи могли найти аддин в каталоге, изучить его возможности и установить пакет из релиза.

Статус выпуска. На 26 ноября 2026 года у Community Store нет опубликованных GitHub Releases. Руководство описывает текущую сборку в разработке, включая загрузку README по языку, страницу аддина в каталоге и список версий установленного аддина. Релизы Community Store

Подключите владельца GitHub и подготовьте репозиторий

  1. Используйте публичный репозиторий, принадлежащий вашему аккаунту или организации на GitHub. Community Store пропускает закрытые и архивные репозитории, форки и репозитории с именем, начинающимся с точки.
  2. Если владельца GitHub нет в списке по умолчанию, предложите пользователям открыть Каталог → Источники и ввести его логин, URL профиля или URL репозитория. Например, https://github.com/ExampleStudio/PanelTool подключит все подходящие репозитории владельца ExampleStudio в этой установке. Публичный каталог доступен без входа, а после входа запросы расходуют квоту GitHub API пользователя.
  3. Опубликуйте GitHub Release. Одного Git-тега или черновика релиза для появления карточки недостаточно. Аддин можно явно обозначить с помощью любой из следующих тем — fusion-addin, fusion360-addin, autodesk-fusion-addin или fusion-360-addin.

Community Store также распознаёт обычный аддин Fusion в дереве файлов выбранного тега. Он ищет JSON-файл .manifest рядом с одноимённым файлом .py, .ts, .js, .dll, .dylib или .cpp. Укажите "type": "addin" и "autodeskProduct": "Fusion" или "Fusion360". Размещайте манифест вне каталогов test, tests, samples, examples и docs. Размер файла должен быть не больше 32 КиБ. Store проверяет до шести кандидатов, отдавая приоритет совпадению с именем репозитория, а затем меньшей глубине пути.

В отсутствие подходящей темы и манифеста в теге Store может обнаружить аддин, проверив подходящий загруженный ZIP с контрольной суммой GitHub и поддерживаемой версией тега. Тема позволяет показать релиз даже без пригодного пакета. Включайте манифест в тег и при наличии темы, чтобы Store мог определить ID аддина и найти его значки в репозитории.

Как подать заявку на добавление доверенного источника

Чтобы ваш профиль или организация GitHub появились в списке источников по умолчанию, подайте публичную заявку. Приложите ссылки на профиль или организацию и на релиз одного из аддинов. Команда Community Store рассмотрит заявку. После одобрения и добавления источника в каталог попадут подходящие аддины этого владельца. Подать заявку на добавление источника

Команда Community Store ведёт список источников по умолчанию в файле trusted-stores.json. Одобрив заявку, команда добавляет логин владельца GitHub в массив owners и вносит изменение в ветку main. Файл лежит за пределами списка путей выпуска аддина. Правка только этого файла обновляет список источников без выпуска новой версии Store. Community Store проверяет изменения при запуске, открытии палитры и проверках каталога. Последний корректный список доступен офлайн, источники, добавленные вручную, сохраняются. В новой установке доступен 4FusionLab до получения корректного списка.

Соберите пакет и опубликуйте релиз

  1. Выберите тег вида v1.2.0 и укажите "version": "1.2.0" в манифесте внутри ZIP. Store сравнивает версии по числам. Поддерживаются от двух до четырёх числовых компонентов, необязательный префикс v и необязательные метаданные +build, которые не учитываются при сравнении. Тег вида v1.2.0-beta.1 для установки не подойдёт. Отмечайте предварительные версии на GitHub как pre-release. Они могут появляться в каталоге со ссылкой на GitHub. Установка и выбор целевой версии в Store используют стабильные релизы.
  2. Загрузите установочный .zip в раздел Assets релиза GitHub для этого тега. Автоматический архив GitHub Source code (zip) исключён. Store требует SHA-256 в метаданных файла на GitHub и сверяет её с загруженными байтами. Отдельный файл .sha256 удобен для ручной проверки, а для проверки в Store нужна сумма из метаданных. Инструкция GitHub по публикации релизов
  3. Положите в ZIP одну папку аддина с одноимёнными манифестом и файлом запуска, а также необходимыми зависимостями. Для переносимости используйте одинаковое написание и регистр имени папки и файлов без расширения. Укажите в id уникальный постоянный GUID и сохраняйте его в манифесте в теге, во всех пакетах и последующих версиях. Store принимает скрипты .py, .ts и .js, нативный .dylib для macOS и 64-битную библиотеку AMD64 PE DLL для Windows. Исходный .cpp помогает обнаружить аддин, а для установки нативной версии нужна библиотека. Лимиты ZIP — 150 МиБ при загрузке, 450 МиБ после распаковки и 15 000 записей. Используйте обычные относительные пути без символических ссылок, имён, различающихся только регистром, и зарезервированных имён Windows. Манифест и структура аддина в документации Autodesk
  4. Укажите в supportedOS системы, которые действительно поддерживает пакет — windows, mac или windows|mac. До загрузки Store проверяет имя ZIP, при подготовке к установке — манифест и файл запуска. Отметка совместимости в списке пакетов не подтверждает работу бинарного файла и его зависимостей в Fusion.

Разделяйте обозначения системы и архитектуры дефисами, подчёркиваниями или точками. Store распознаёт mac, macos, darwin, osx, win, windows, win64 и windows64. Указывайте x64 (также amd64, intel, x86_64) или arm64 (также aarch64) вместе с явным обозначением системы. Для Windows при выборе пакета ожидается x64. Для macOS Store использует архитектуру, которую сообщает его процесс. Архивы, помеченные как исходники, отладочные, Linux или 32-битные сборки, не подходят. Если в списке несколько ZIP, окно выбора отмечает, какие подходят для текущей системы. Проверяйте сам пакет в Fusion на каждой поддерживаемой платформе.

Свяжите уже установленный аддин

Если аддин установлен вручную или клонирован из Git, зарегистрируйте его папку в Fusion, чтобы он появился в разделе Мои аддины. Добавьте владельца GitHub в Источники. Для поиска версий Community Store использует сохранённую привязку собственных установок или GitHub-адрес origin локального клона. В остальных случаях Store ищет единственное совпадение в каталоге.

Самый надёжный признак совпадения — один и тот же ID манифеста. Store также может сопоставить аддин по имени без расширения из найденного манифеста, по имени репозитория при отсутствии манифеста или по GitHub origin. Если оба ID известны и различаются, совпадающего имени недостаточно. Для обновления папки без ID нужен точный GitHub origin, а пакет должен совпасть с аддином по имени. Используйте постоянный ID и единое имя, чтобы избежать неоднозначных совпадений. После сопоставления каталог может показать отметку Установлен. Применение обновления выполняется отдельным действием.

Поставщик и автор в списках Каталог показывает владельца репозитория GitHub и автора из манифеста релиза, если он известен. В разделе «Мои аддины» автор берётся из Fusion, а владелец репозитория GitHub отображается для связанных установок.
Описание Описание репозитория GitHub. Если его нет, Store берёт первую подходящую строку из текста выбранного релиза. Карточка показывает короткую выдержку без форматирования Markdown.
Автор и установленная версия В шапке страницы приоритет у автора из локальной регистрации Fusion. Также Store показывает поле author из манифеста, если он обнаружен для выбранного релиза. Установленная версия берётся из локального манифеста или, если она не указана в нём, из регистрации Fusion.
Версия в репозитории и дата публикации Тег и дата публикации выбранного GitHub Release.
Заметки о релизе Текст выбранного GitHub Release отображается как Markdown, до 16 000 символов. Поместите краткое описание изменений в начало. В качестве версии показывается тег релиза.
Целевые версии В разделе Мои аддины → Целевая или в шапке страницы аддина для сопоставленной установки можно следовать за последним релизом или выбрать доступный стабильный тег из истории. Список отсортирован по числовой версии и включает релизы с подходящим ZIP и контрольной суммой GitHub. История загружается в фоне, а при недоступности GitHub могут отображаться сохранённые версии.

Сначала Store проверяет последний стабильный релиз по данным GitHub. Если его нельзя установить на текущей системе, Store выбирает первый подходящий стабильный релиз в порядке выдачи истории. Если подходящего релиза нет, карточка всё равно может показывать последний релиз или первую опубликованную запись истории без кнопки установки. README и заметки на странице аддина относятся к релизу, выбранному для каталога, даже если для установленного аддина пользователь указал другую целевую версию.

Оформите README для каталога

Положите файлы README.md и README.ru.md в кодировке UTF-8 в корень репозитория на теге релиза. Store загружает файлы по тегу, даже если в основной ветке есть более свежая копия. Для английского используется только README.md. Для русского Store сначала пробует README.ru.md, затем README.md, если русского файла нет, он пуст или недоступен. Русский файл из одних пробельных символов может помешать переходу на английский, тогда README будет показан как недоступный. Лимит на файл — 96 КиБ. Соблюдайте регистр имени и включайте обе версии и изображения в коммит до создания тега.

В разделе Настройки → Язык интерфейса можно выбрать английский, русский или язык системы. Для неподдерживаемых языков системы используется английский. Настройка меняет интерфейс Store и выбор README. Локализуйте команды и элементы управления своего аддина отдельно. Локализованные описания в манифесте предназначены для Fusion. Пишите описание репозитория и заметки о релизе на тех языках, которые должны увидеть пользователи. Store показывает эти поля GitHub в исходном виде при любом языке интерфейса.

На странице аддина есть раздел Читать README и ссылка на выбранный файл на GitHub. Во время загрузки и при недоступности показывается соответствующий статус. Поддерживаются заголовки, абзацы, списки, выделение, цитаты, код и таблицы. Допускается ограниченный набор HTML-элементов, например <details> и <summary>. Интерактивные вставки, скрипты, стили и большинство HTML-атрибутов удаляются. Используйте явные ссылки Markdown. HTTPS-ссылки открываются в браузере, а относительные ссылки и ссылки на якоря разрешаются относительно файла на GitHub для выбранного тега. Обычные URL в тексте автоматически не становятся ссылками. В заметках о релизе используется тот же рендерер. Относительные ссылки ведут от README.md на теге, встроенные изображения не загружаются.

Логотипы и скриншоты

  • Используйте PNG, JPEG (.jpg или .jpeg) или WebP размером до 1 МиБ и 4096 пикселей по каждой стороне. Указывайте обычные относительные пути на выбранном теге в прямых ссылках Markdown на изображения или в HTML <img src="…"> с кавычками. Внешние картинки, стандартные бейджи, SVG и GIF не загружаются. Одного определения ссылки в Markdown недостаточно, чтобы Store загрузил картинку. Если картинку нельзя показать, остаётся альтернативный текст.
  • Чтобы изображение из README также могло попасть в галерею, положите его в папку, как media/screenshot.png. Файл в корне или с icon либо logo в имени считается кандидатом на роль логотипа. Изображения README и вложения релиза с badge, banner, avatar или shield в имени пропускаются. Store рассматривает до 12 разных путей из README и пытается показать до четырёх изображений внутри текста, начиная со скриншотов.
  • Store сначала пробует явно указанный значок, затем вложение релиза с icon или logo в имени, затем один из двух первых подходящих по приоритету PNG из папки resources/ аддина на теге, а затем логотип из README. Поддерживаемые имена PNG в resources/ — 32x32@2x.png, 64x64.png и 32x32.png. Для галереи Store сначала пробует явно указанные изображения, затем другие подходящие вложения релиза, а после них скриншоты из README. Store рассматривает до восьми подходящих вложений с изображениями. Страница аддина показывает до трёх скриншотов. Карточка в списке показывает первый скриншот, при его отсутствии — логотип или заглушку.
  • Чтобы явно указать изображения, добавьте в корень тега community-store.json с относительными путями к растровым файлам. Используйте поля icon, preview и до шести путей в screenshots. Store читает конфигурацию, если находит её в дереве тега при поиске распознанного манифеста. Конфигурация и вложения релиза общие для обоих языков. В отдельных README можно сослаться на разные иллюстрации.

Проверьте результат

  • Карточки нет. Проверьте логин владельца в Источниках, публичность репозитория, наличие опубликованного релиза и подходящей темы либо манифеста на выбранном теге. Обновите каталог. Если GitHub ограничил запросы, проверьте время следующей попытки или войдите в аккаунт.
  • Карточка есть, кнопки установки нет. Откройте выбранный релиз на GitHub. Проверьте, что релиз стабильный, тег распознаётся как версия, подходящий ZIP прикреплён и у него есть контрольная сумма. Если установка начинается и завершается ошибкой, сверьте ID и версию манифеста, имена папки и файла запуска, supportedOS и содержимое ZIP.
  • У установленного аддина нет списка версий. Проверьте источник владельца, локальную регистрацию в Fusion, ID манифеста и GitHub origin. Убедитесь, что совпадение однозначно и в истории есть стабильный пакет под вашу систему. Повторите проверку, если история ещё загружается или недоступна.
  • Не тот язык или README отсутствует. Проверьте Язык интерфейса, тег на странице аддина, регистр имён файлов в корне, их размер и кодировку UTF-8. Если вместо русского виден английский, откройте русский файл на GitHub по этому тегу. Чтобы Store увидел новую версию файла из основной ветки, включите её в следующий тег релиза.
  • Логотип или скриншот отсутствует. Проверьте относительный путь и регистр на теге, формат и размер файла, порядок отбора в галерею и лимит картинок внутри текста. Проверьте английскую и русскую версии по отдельности.
